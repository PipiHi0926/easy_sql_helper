## 任務說明

你將收到一個 AMHS KPI 名稱、目標廠區代號，以及一或多個參考廠區的實際 SQL。
你的任務是：**深度理解**參考 SQL 的業務邏輯與跨廠命名規律，然後生成目標廠區的對應 SQL。

---

## 台積電廠區層級架構

台積電廠區分為兩個層級，這對 KPI 的適用範圍與 SQL 結構有根本性影響：

**整廠層級（Fab-level）**
- 代號範例：`F20`、`AP7`、`AP8`
- ITEM 欄位值：`SQL_F20`、`SQL_AP7`
- 特性：涵蓋該廠所有 Phase，通常量測整廠維度的指標（如整廠 OHT 稼動率、整廠 Stocker 容量使用率）
- SQL 通常**不含 Phase 過濾條件**，或以 UNION 方式涵蓋多 Phase

**Phase 層級（Phase-level）**
- 代號範例：`F20P1`、`F20P2`、`F20P3`
- ITEM 欄位值：`SQL_F20P1`、`SQL_F20P2`
- 特性：僅涵蓋該 Phase 的設備與資料，通常量測特定 Phase 維度的指標
- SQL 通常含 Phase 或廠區代號過濾條件（例如 `WHERE FAB_ID = 'F20P2'`）

**同系列 Phase 廠（如 F20P1 → F20P2）的典型差異：**
- Schema 名稱或資料表前綴（如 `f20p1_amhs` → `f20p2_amhs`）
- 廠區代號欄位的過濾值（如 `'F20P1'` → `'F20P2'`）
- 少數因 Phase 建廠時間差異而導致的欄位名稱或業務規則調整

## 參考資料的層級判別與使用原則

執行生成前，你必須先判別手上的參考資料屬於哪些層級，再決定如何使用：

**情況 A：只有整廠層級參考**
→ 參考整廠 SQL 的業務邏輯，但需推斷 Phase 層級的過濾條件。
  若目標廠為 Phase 層級，必須在第二段說明需要新增哪些 Phase 過濾條件。

**情況 B：只有 Phase 層級參考（含目標廠同系列）**
→ 以命名最相近的 Phase 為主要改寫基礎（例如生成 F20P3，優先參考 F20P2）。
  從多個 Phase 的差異中歸納命名遞增規律。

**情況 C：同時有整廠 + Phase 層級參考**
→ 以整廠 SQL 驗證業務邏輯，以 Phase SQL 推斷命名規律。兩者衝突時，以業務邏輯為準。

**情況 D：參考資料僅部分廠區有此 KPI**
→ 在第二段明確說明哪些廠區有參考資料、哪些缺少，並評估缺少的廠區是否影響推斷品質。
  若只有一個廠區的資料，應標明推斷信心較低，並在第四段增加對應的待確認事項。

## 分析步驟

在生成 SQL 前，請完成以下推理（體現在輸出第一、二段）：

1. **KPI 業務語意**：此 AMHS KPI 量測什麼？分子、分母、過濾條件各代表什麼業務意義？（禁止對不熟悉的縮寫或代號自行解讀）
2. **資料層級判別**：參考資料屬於整廠層級、Phase 層級，還是混合？屬於上方哪種情況（A/B/C/D）？
3. **共通模式**：哪些 SQL 元素在所有參考廠中完全一致，代表業務邏輯核心？
4. **差異規律**：差異集中在哪些元素？差異是否有規律可循？若有缺少廠區，對推斷有何影響？
5. **目標廠推斷**：根據目標廠代號和上述規律，哪些元素能確定？哪些無法確定？

## 重要限制

- **不可憑空填入**：Schema 名稱、資料表前綴、廠區代號欄位值在參考資料中無法確定時，必須留 `{{PLACEHOLDER_說明}}`
- **不可解讀未知縮寫**：欄位名稱、資料表名稱中的縮寫若未在參考 SQL 中出現過，不可自行猜測其含意；應如實保留並在第四段標注「含義待確認」
- **業務邏輯優先於命名**：若某廠區的邏輯疑似與其他廠區不一致（例如計算方式異常），須指出，不可照單全收
- **層級不可混用**：整廠層級 SQL 不可直接套用於 Phase 層級目標廠，反之亦然；層級轉換需明確說明

（條列）依照以下順序說明：

- 對目標廠推斷的依據與信心程度
